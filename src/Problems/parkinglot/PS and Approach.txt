Designing a Parking Lot System

Requirements:

The parking lot should have multiple levels, each level with a certain number of parking spots.
The parking lot should support different types of vehicles, such as cars, motorcycles, and trucks.
Each parking spot should be able to accommodate a specific type of vehicle.
The system should assign a parking spot to a vehicle upon entry and release it when the vehicle exits.
The system should track the availability of parking spots and provide real-time information to customers.
The system should handle multiple entry and exit points and support concurrent access.

Step 3 and 4 deep dive

When assigning responsibility, ask one question:
Which object actually owns this data?
Behavior should live with the data it operates on. This is the foundation of Object-Oriented Design and encapsulation.

1. principle -> Objects represent real ownership
    Wrong Design
    ParkingLot.canVehicleFit(spot, vehicle)

    ParkingLot shouldn't know how a spot works.
    That leaks internal logic.

    Correct Design
    ParkingSpot.canFit(vehicle)
    Behavior is attached to the object owning the state.


2. Responsibility Assignment Rule (The Expert Mental Model)

Use this 3-step rule.

    Rule 1 — Behavior lives where the data lives

    Rule 2 — The coordinator orchestrates objects
    Higher-level objects coordinate, not implement logic.

    Example:
    ParkingLot coordinates floors.

    ParkingLot
       parkVehicle()

    But it doesn't implement parking logic.
    Instead it delegates.

    ParkingLot.parkVehicle(vehicle)
         -> ask floors for available spot
         -> assign vehicle
         -> generate ticket

    ParkingLot is an orchestrator, not executor.


   Rule 3 — Traversal objects search collections

   Objects that hold collections perform search.
   Example:

   ParkingFloor
       List<ParkingSpot>

   So:
   ParkingFloor.getAvailableSpot(vehicle)
   makes sense.
   Because it owns the list.

4. Why Not ParkingLevel.parkVehicle() ?

    Why not make ParkingLevel.parkVehicle()

    We decide based on system boundary responsibility.

    Who is the entry point of the system?

    In real life:

    Driver interacts with ParkingLot, not a floor.

    Driver → ParkingLot
    ParkingLot → Floor
    Floor → Spot

    So API should start at ParkingLot.

    This is Facade pattern thinking.

    Architecture View
    Client
       ↓
    ParkingLot (system entry point)
       ↓
    ParkingFloor (collection manager)
       ↓
    ParkingSpot (state owner)


5. Relationship Thinking (Step 3)

    Relationships are basically composition trees.
    Ask:
    What contains what?

    Parking Lot example:

    ParkingLot
        └── ParkingFloor
                └── ParkingSpot

    This is HAS-A relationship.

    Identify Relationship Types

    In LLD we mostly use:

    Composition (Strong Ownership)
    ParkingLot → ParkingFloor
    ParkingFloor → ParkingSpot

    Floor cannot exist without lot.

    Association
    Ticket → ParkingSpot
    Ticket → Vehicle

    Ticket references them but doesn't own lifecycle.

    Dependency
    PaymentService → Ticket

    Uses it temporarily.


6. Expert Trick for Step 3

Draw a containment tree first.

Example:

ParkingLot
    floors
        spots

Then attach external objects:

Vehicle
Ticket
Payment



7. So there are Pure Domain Objects -> Pure State + Rules (Spot, Floot, Vehicle, Ticket), then there
are Orchestrator (ParkingLot, ParkingService), and then there is Infra -> External Systems (PaymentGateway, DisplayBoard, NotificationService)



So in short:
1) Identify Entities 2) Draw containment tree 3) Identify data ownership 4) Attach behavior 5) Orchestrator
